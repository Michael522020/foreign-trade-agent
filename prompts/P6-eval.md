# P6 — 评估与回归

> 前置检查：至少 P1 + P2 + P3 已跑通，且有一个真实的 30 天窗口数据（或明确的"暂无数据"声明）。
> 没有数据就不要做这一步——造一组漂亮数字是这套系统最容易犯的错。

## 目标

回答一个问题：**这套系统让业务员变强了，还是只是让他们更忙了？**

## 一、先建基线（在改造前测，或从历史数据回算）

| 指标 | 口径 | 数据源 |
|---|---|---|
| 人均日有效触达数 | 有实质内容的首次触达 / 人 / 天 | 邮件系统日志 |
| 冷邮件回复率 | 有回复的邮件 / 成功投递邮件 | 发件箱 |
| 正面回复率 | 表达兴趣/索要资料的回复 / 成功投递 | 人工标注（抽 100 条校准） |
| 询盘→报价 转化率 | 生成报价的询盘 / 有效询盘 | CRM |
| 报价→订单 转化率 | 成交 / 报价 | CRM |
| 首响应时长中位数 | 询盘到首次回复 | 平台后台 |
| 单条有效线索成本 | 渠道总投入 / 有效线索数 | 财务 |

**必须同时记录"改造前"和"改造后"，否则无法归因。**

## 二、过程指标（提前 2–4 周就能看出问题）

| 指标 | 危险阈值 | 说明 |
|---|---|---|
| 退信率 | > 2% | 名单质量或验证环节有问题 |
| 投诉率 | > 0.1% | 立即降量，检查文案与名单相关性 |
| 草稿采纳率 | < 40% | 业务员不用，说明文案不符合他们的判断 |
| 草稿编辑率 | > 70% | 生成的内容需要大改，等于没生成 |
| 队列清空率 | < 60% | 每日给太多，或质量不够 |
| `REJECTED_UNAPPROVED_FACT` 频次 | 上升 | 说明生成端在编造事实，检查上下文注入 |

**草稿采纳率和编辑率是最重要的两个指标。** 它们直接反映"这东西有没有用"。如果业务员每次都要改 80%，那 AI 只是增加了一道工序。

## 三、离线回归集（防止改一个地方坏另一个地方）

建一个 `eval/golden_set/`：

- **50 条真实询盘**，人工标注 `inquiry_type`（六类）
- **30 条真实海关记录**，人工标注"是否值得开发"（是/否/不确定）
- **20 个真实客户场景**，人工标注"开发信里应该提到什么/不应该提什么"
- **10 个报价场景**，含边界（低于成本、汇率波动、DDP、认证缺失）

每次改 prompt 或改规则，跑：
```bash
python -m src.cli eval run --suite eval/golden_set/ --report reports/eval_{date}.json
```

输出：
```
询盘分类准确率     0.84  (基线 0.71)
  └ PRICE_PROBE 误判为 SPAM_BLAST: 3 例  ← 这是最贵的错误
线索评分排序相关性  0.61  (Spearman, vs 业务员人工排序)
开发信事实合规率   1.00  (50/50 全部通过白名单)
报价自检拦截率     1.00  (10/10 正确拦截)
```

**必须看混淆矩阵，不只看准确率。**
把 `PRICE_PROBE` 误判成 `SPAM_BLAST`（丢弃真实客户）的代价，远高于把 `SPAM_BLAST` 误判成 `PRICE_PROBE`（多花 5 分钟）。所以评估要按"错误的代价"加权，不是按错误数量。

```python
COST_MATRIX = {
    ("PRICE_PROBE", "SPAM_BLAST"):  100,   # 丢掉真实客户
    ("REAL_RFQ",    "SPAM_BLAST"):  200,   # 丢掉大单
    ("SPAM_BLAST",  "PRICE_PROBE"):   1,   # 浪费 5 分钟
    ("REAL_RFQ",    "PRICE_PROBE"):  10,   # 慢一步
}
```

## 四、A/B 测试的正确做法

- 一次只改一个变量（主题行 / 开场句 / CTA / 长度 / 发送时段）
- 每组至少 200 封再看结论
- 分流要随机，且**同一公司不能同时进两组**
- 结论必须带样本量和置信区间，不写"提升了 30%"就完事

## 五、失败案例库（最有价值的资产）

建 `eval/failure_cases/`，每条记录：
```
id, 场景, 系统输出, 正确输出, 错误类型, 代价(高/中/低), 修复状态
```

优先修「高代价 + 高频」的。低代价低频的，记下来就好，不要过度工程。

典型的高代价失败：
- 把真实买家判成垃圾询盘
- 报价漏算海运或退税
- 声称未持有的认证
- 对欧盟客户发无 LIA 记录的冷邮件
- 在正文里承诺了排期做不到的交期

## 验收

```bash
python -m pytest tests/eval/ -v
python -m src.cli eval run --suite eval/golden_set/ --report reports/eval_$(date +%F).json
python -m src.cli report monthly --month 2026-10
```

报告必须包含：
1. 基线 vs 现状对比表（每项标口径、样本量、时间窗口）
2. 加权混淆矩阵（不是单纯准确率）
3. 失败案例 Top 5（按代价 × 频次排序）
4. **明确写出"哪些结论数据不足，暂不能判断"**

第 4 项是硬要求。宁可写"样本不足"，也不要给一个看起来专业的伪结论。

## 不要做的事

- 不要用"AI 评分"评估"AI 输出"（自我评估会系统性偏高）。
- 不要在样本量 < 200 的情况下宣称百分比提升。
- 不要只报好数字。失败案例库的价值大于成功指标。
- 不要优化"回复率"到损害"正面回复率"。用"thanks, remove me"换来的回复率是负资产。
